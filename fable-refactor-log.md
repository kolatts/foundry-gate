### D-008: Routers/classifiers investigation → aliases yes, classification no
**Date:** 2026-09-01
**Decision:** Adopt (plan `plans/25-model-aliases-routing.md`): model alias map +
per-product allowlist as an APIM policy fragment (S effort), failover-only dynamic
routing (already #83), optional off-by-default `llm-content-safety`, extended token
metric dimensions folded into #84. Reject for CLI traffic: Azure Foundry Model Router
(GA Nov 2025 — OpenAI-schema only so Claude Code can't reach it; context window bounded
by smallest pool model; nondeterministic routing destroys prompt-cache continuity;
~$0.14/M markup), APIM semantic caching (Redis+embeddings cost, ~zero duplicate rate in
agentic traffic, stale-hit-into-tool-loop risk), and gateway-side prompt classifiers
(serial LLM hop on every request; Claude Code already self-classifies via its haiku
lane). Watchlist: APIM Unified Model API (preview, OpenAI-facing).
**Why:** Every reference gateway (LiteLLM, OpenRouter, Portkey, MS AI Hub Gateway)
centers aliases + explicit conditions + health failover; classification-based routing is
a chat feature that breaks the agent-harness contract (pinned model, cache prefix
continuity, context guarantees). Full sourced findings in the router research report
(agent output, summarized in plan 25).

- **E-006 (idempotency):** Re-PUTing an existing Anthropic deployment via template
  (same properties + modelProviderData) returned Conflict and drove the deployment to
  provisioningState=Failed — Anthropic deployments are NOT cleanly idempotent under
  ARM redeploy while active. Recovery: delete + recreate. Implication for #13/#20:
  Bicep re-runs must not touch existing Anthropic deployments (deploy-if-missing), and
  the control plane should treat deployment updates as delete/recreate with drain.

- **E-007 (Anthropic provisioning fragility, 2026-09-01 13:00–14:10 UTC):** Observed
  live on Imagile Paid: (a) the first Claude create per fresh account succeeds; (b) ARM
  re-PUT of an existing/creating Anthropic deployment → Conflict or async Failed;
  (c) after delete/recreate cycles, creates in the SAME account start failing — first
  asynchronously (Creating ~5 min → Failed, opaque InternalServerError, Activity Log
  carries no marketplace detail), then even synchronously (immediate 500), including
  under fresh deployment names; (d) `provisioningState=Failed` deployments show
  `deploymentState=Running` but the data plane refuses traffic until Succeeded;
  (e) OpenAI deployments in the same account provision instantly and reliably
  (gpt-4.1-mini: sync Succeeded). Conclusion: Claude deployment lifecycle churn is
  dangerous; treat Anthropic deployments as create-once-per-account, avoid
  delete/recreate loops, and expect multi-minute async validation. Direct input for
  #20/#64 (provisioning orchestrator must be conservative + poll to terminal state).

### D-009: Tagging + organization for scale (user request)
**Date:** 2026-09-01
**Decision:** Every resource carries `standardTags`: `workload=foundrygate`,
`environment`, `managed-by=bicep`, `repo`, plus `fg-role`
(gateway|foundry|monitoring) and, on Foundry accounts, `fg-region-role`
(primary|pool-member). Scale model documented in `infra/main.bicep`: regions scale
*inside* a stack (foundryRegions → pool members); subscriptions scale by deploying the
same template per subscription — because Claude Global Standard quota is pooled
per-subscription per-model, extra subscriptions (not extra same-subscription
deployments) are what multiply Claude headroom. Cross-subscription cost/inventory
queries filter on workload+environment+fg-role uniformly.
**Why:** Asked for explicitly by the user mid-session; also required for the cost
rate-card work (#84) to attribute Claude Marketplace meters across stacks.
