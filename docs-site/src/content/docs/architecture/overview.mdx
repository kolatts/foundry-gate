*The plain-English version of this page is [Why FoundryGate?](/foundry-gate/getting-started/why-foundrygate/); the full platform detail lives in [Feasibility &amp; Strategic Direction](/foundry-gate/architecture/feasibility/) and the [reference section](/foundry-gate/reference/configuration/).*

FoundryGate is a governance and access-management layer for Azure AI Foundry. It provisions the gateway and the model deployments — Claude models are set up by the infrastructure deploy, and admins manage OpenAI model deployments from the UI — then adds per-developer budget enforcement, individual key lifecycle management, and Entra-driven provisioning on top of them.

## System diagram

The system splits into two planes. The **data plane** is the APIM v2 gateway: every
developer request passes through it, and every limit is enforced there, in real time. The
**control plane** is the FoundryGate app: it never sees a model request — it decides who
gets a key, which tier product that key lives under, and reconciles what the gateway
reported afterwards. Solid arrows are the request path; dashed arrows are out of band.

<SystemDiagram />

Two details on the diagram are ground truths worth stating plainly:

- **Enforcement is the solid path.** `llm-token-limit` in each tier product's policy
  decides `403` / `429` on the request itself, keyed on the developer's APIM subscription.
  Nothing in the control plane is consulted per request.
- **Reconciliation is the dashed path.** The Functions read the gateway's
  `ApiManagementGatewayLlmLog` table to keep `QuotaAllocation.TokensUsed`, dashboards, and
  cost figures authoritative. If that sync stopped, enforcement would continue unchanged.

## Entra ID sync — how access follows your org chart

FoundryGate uses the Microsoft Graph API to keep developer access in sync with your Entra directory. It calls Graph as its own managed identity, granted read-only Graph application roles — there is no client secret to store or rotate. This is how access governance works without any manual admin work after initial setup.

<Aside type="note">
**Group sync moves budgets, not accounts.** It never creates, deactivates or deletes a `User`, and never revokes a key. Leaving a synced group simply drops that developer back down the five-level resolution chain below — usually to the system default. Losing the Entra *application assignment* is the separate, account-level event, handled by bulk user sync.
</Aside>

<Aside type="caution">
**Departures are hard**: a developer who loses their Entra assignment to the FoundryGate application is deactivated, and their APIM subscription is *deleted* — not just suspended. Their key stops working immediately. This is intentional, and it is a different thing from running out of budget: quota exhaustion never touches the subscription at all — it's a real-time `403` at the gateway that clears on reset or approval, while Entra departure permanently revokes. Bulk user sync runs the same deletion — it is the same pipeline the admin button calls.
</Aside>

### Bulk user sync

`POST /users/sync` pages through all users assigned to the FoundryGate service principal via Graph and upserts them. New users get a record with the default quota; departed users run the same deprovision pipeline an admin deactivation does — subscription deleted, allocation hard-stopped, pending requests rejected — so the sync and the admin button can never drift apart. Useful for an initial import of your entire org before any developer has logged in.

Each departure is its own unit of work, deliberately: a subscription deletion cannot be rolled back, so batching several into one transaction would mean a single failed ARM call erasing the record of deletions that had already happened. A departure the gateway refuses is counted (`failedCount`), logged, and retried on the next run — the rest of the batch still lands.

Assignments granted to a **group** count as assignments to its people: each one is flattened to the group's transitive members (nested groups included) and merged with the directly assigned users, so assigning `SG_AI_Developers` to the enterprise application is a fully supported setup rather than a partial one. The one case that changes behaviour is a group the API cannot read — that run has an incomplete picture of who is assigned, so it adds and updates but deactivates nobody and says so (`skippedGroupAssignmentCount`).

## Five-level quota resolution

When a developer's allocation is created or updated, `IQuotaResolutionService` walks this chain — first match wins — and the result selects the **tier product** the developer's APIM subscription lives under:

<QuotaChain />

The resolved value is written to `QuotaAllocation` for the current period, and the subscription is created under (or moved to) the matching tier product. Admins can see which level resolved each developer's quota in the user detail view. Tiers exist because APIM's `token-quota` attribute accepts only literals — one policy cannot read a per-user number — so each tier is a product with its own rendered policy.

**A budget is a tier.** Resolution picks a tier, not just a number: every quota the
control plane accepts must equal a configured tier's cap (5M → *Standard*, 20M →
*Power*, with the shipped caps) or be unlimited, so the number written to the allocation
and the tier the gateway enforces are the same thing. Admins pick from `GET /quota/tiers`
rather than typing a figure. A legacy or hand-edited value that matches no tier is never
rejected on read — it is enforced at the next tier up and flagged **gateway-capped** so an
admin can correct it. The allocation records the level, the tier, and the flag, and
moving the developer's subscription onto the tier product is what actually changes
their budget.

**Resets never zero usage.** The gateway's monthly window resets itself at the UTC month
boundary, so the monthly job and the admin's manual `POST /quota/reset` only (re)resolve
every active developer's allocation for the current UTC month: new rows start at zero,
existing rows are re-resolved but keep their reconciled usage, and the hard-stop mirror is
cleared. Running it twice in a month is safe and audited once per run.

## APIM enforcement — how limits actually block traffic

FoundryGate doesn't rely on a database flag being checked on every request — and it no
longer relies on a polling loop either. Enforcement lives in the gateway's
`llm-token-limit` policy, keyed on each developer's APIM subscription:

- **Monthly budget**: `token-quota` + `token-quota-period="Monthly"` — the developer's
  requests get `403` the moment the budget is exhausted, in real time, on the request
  path. Quota windows are UTC calendar months, so they reset themselves at month start.
- **Burst control**: `tokens-per-minute` — a per-developer TPM cap returns
  `429 + Retry-After` for one developer's runaway agentic loop without touching anyone
  else's traffic. Claude Code and Codex CLI both back off on this automatically.
- Both work on the **Anthropic Messages** path (Claude Code) and the **OpenAI** path
  (Codex CLI) — the LLM policies understand both payload schemas on APIM v2 tiers.

Quota tiers are modeled as APIM **products** (Standard / Power / Unlimited): each
product's policy carries that tier's budget and TPM cap, and changing a developer's
quota means moving their subscription between products. Subscription *suspension* is
reserved for deactivation and offboarding — not quota exhaustion.

The usage-sync Function still runs, but as **reconciliation**, not enforcement. It is a
.NET isolated worker on a Flex Consumption plan — scale-to-zero, so it costs nothing between
ticks — reading the gateway's own log with the Function App's managed identity. The query it
runs is a plain `.kql` file checked into the repo, so an operator can paste it into the Log
Analytics blade and get exactly the number the Function got:

<Aside type="note">
**These totals can read low, never high.** One request produces several log entries — the
request, the response, and a further entry per 32 KB chunk of either — all carrying the same
per-request token counts, so the query collapses them to one row per request before adding
anything up. What it cannot recover is a request whose counts were never logged at all: a
stream the client interrupts can leave the token usage missing or inaccurate at the source.
So reconciled usage is a floor. That is survivable precisely because nothing depends on it —
the gateway's own counter, the one that returns `403`, is separate and authoritative.
Per-developer cost estimates (tokens × rate card) build on these figures and are tracked
separately.
</Aside>

<Aside type="note">
**Deployment-level limits are mitigated, not repealed.** Foundry still enforces shared
per-model rate pools (RPM / uncached-input TPM / output TPM for Claude). FoundryGate's
gateway smooths and reroutes around them — per-developer TPM caps for fairness, backend
pools with circuit breakers for failover — but total capacity is still bounded by the
platform. See [Azure AI Foundry Rate Limits](/foundry-gate/reference/azure-rate-limits/)
for the ceilings and [Feasibility &amp; Strategic Direction](/foundry-gate/architecture/feasibility/)
for the mitigation architecture.
</Aside>

## APIM key lifecycle

A developer's key *is* an APIM subscription, created under their tier product. Only
people-lifecycle events change its state — there is no suspended state:

<KeyLifecycle />

**Rotate** — `POST /keys/me/rotate` (or an admin's `POST /keys/{userId}/rotate`) calls
`regeneratePrimaryKey` *and* `regenerateSecondaryKey` on the subscription: the primary key
the developer holds is replaced instantly and shown once, and the secondary — which
FoundryGate never issues or stores — is replaced too, so no credential outlives a rotation.
The subscription stays `active` with its counters intact. Stored keys are wrapped with a
Key Vault RSA key before they reach SQL; `GET /keys/me` shows only the last four characters,
and `POST /keys/me/reveal` decrypts on demand (audited) rather than caching anything in the
browser.

Both of those routes are capped **per signed-in person** by the control plane — five reveals
and three rotations a minute — because a stolen access token could otherwise replay them for
the plaintext key indefinitely, leaving nothing behind but a long run of audit rows. Over the
cap the control plane answers `429` with a `Retry-After` header. The admin routes are not
capped: an admin rotating a compromised team's keys is exactly the work a cap would obstruct.

**Change quota** — the control plane re-scopes the subscription to the new tier's
product. The new product's `llm-token-limit` applies from the next request, and because
the gateway's monthly counter is keyed on the subscription *within* a product, the
developer's used-so-far count restarts for the new tier (live validation of the mid-month
move is tracked in #88). No state change.

**Quota exhausted / burst** — the gateway's `token-quota` returns `403` for the rest of
the calendar month; its per-minute token cap returns `429 + Retry-After`. The subscription
stays `active`; the key keeps working the moment the window resets. Nothing to undo.

Two different subsystems can answer `429`, and the URL tells them apart: one from the
**gateway** origin means the developer's per-minute *token* budget is spent, and one from the
**control plane** (`/api/v1/keys/me/*`) means they asked to reveal or rotate their key too
often. Both carry `Retry-After`; only the first has anything to do with quota.

**Delete** — admin deactivation (`POST /users/{id}/deactivate`), Entra departure, or
admin key revocation (`DELETE /keys/{userId}`): `DELETE /subscriptions/{sid}` removes the
subscription entirely and the key stops working immediately. Re-activation
(`POST /users/{id}/activate`) runs the provision pipeline again — reusing an orphaned
subscription if a previous deprovision left one behind — and issues a new key.

## Deploy pipeline

This is the pipeline FoundryGate is built around, as fixed in `CONVENTIONS.md` §CI/CD —
GitHub Actions with OIDC federated credentials and no long-lived Azure secrets. **What
runs today** on every pull request: `ci.yml` (build, tests, format), `claude-review.yml`, and —
by path — `actionlint.yml`, the Docker image build, a Bicep what-if under a read-only
identity, and a Static Web Apps preview of the UI. **What exists on `main`** for the merge path: one workflow, `deploy-all.yml`, which
runs the whole ordered chain (infra → database → API → Functions ∥ UI → post-deploy tests →
summary) against dev. The single-component workflows deliberately have no `push` trigger —
they share a per-environment concurrency lock, and three of them racing meant one deploy was
silently cancelled. They stay as `workflow_dispatch` buttons for redeploying one component.
Gating it all: six GitHub Environments (`dev`, `dev-plan`, `ui-preview`, `production`,
`dev-destroy`, `prod-destroy`); `dev` is restricted to protected branches, so no pull request
can reach the identity that is Owner on the subscription. The two Environments a pull request
*can* reach are deliberately tiny: `dev-plan` is Reader on the subscription and does nothing but
a what-if, and `ui-preview` holds a single custom role — `FoundryGate SWA Preview Publisher`,
defined in `infra/modules/swa-preview-role.bicep` — assignable only on the dev Static Web App.
A pull request runs its own copy of the workflow files, so the identity, not the workflow, is
the boundary. **What has not happened yet**: a run against Azure. That needs the owner-side OIDC
setup (#109) and is the live validation tracked in #105. Badges on the diagram mark the
difference; the [CI/CD reference](/foundry-gate/reference/ci-cd/) lists every workflow, trigger
and variable.

<DeployPipeline />

The database stage is the one with moving parts: the runner's IP is whitelisted on the SQL
server, the workflow waits for firewall propagation and probes port 1433, then the
`FoundryGate.Database` dacpac is deployed with DacFx (data-loss blocked unless a reviewed
`allow-data-loss` override is passed) and reference data is seeded. Two steps then close
the loop that Bicep cannot: the API and Functions managed identities get their contained
database users (`db grant-identities` — an Entra-only SQL server cannot grant a managed
identity access through ARM), and the runner's own firewall rule is removed again, along
with any left behind by a cancelled earlier run. Bicep re-runs pass
`createModelDeployments=false` because Anthropic model deployments are create-once under
ARM, and always pass the image the API is currently running so a re-run never resets it.
That makes the ownership split explicit: Claude deployments belong to the infrastructure
deploy end to end (created once, never re-PUT, never deleted from the app), while the API
and admin UI list everything and manage OpenAI-format deployments
(`/api/v1/foundry/deployments`, see the [API reference](/foundry-gate/reference/api/#foundry)).
Code deploys read resource names from the infra deployment's outputs rather than from
GitHub variables — the only variables are the three OIDC identifiers and the Entra client
ids.
