## In plain words

Your company runs AI models in Microsoft's cloud, and developers use them through
tools on their laptops. The problem: out of the box there's no way to give each
developer their own key, their own monthly budget, or their own usage meter — it's
one shared pool, and one person can drain it for everyone. FoundryGate fixes that.
Each developer automatically gets a personal key and a monthly AI budget; every
request is counted; when the budget runs out, requests stop instantly; and asking
for more is one click to request, one click to approve.

The rest of this page explains the same idea in more technical terms. For the
next level of detail, see the [system overview](/foundry-gate/architecture/overview/).

## The gap, technically

Azure AI Foundry is excellent at what it does: hosting model deployments and exposing them through Azure API Management. But when you move from a single team's prototype to an org-wide AI platform, you hit a wall — Foundry was designed for deployment management, not developer access governance.

## What Foundry gives you out of the box

When you set up Azure AI Foundry with APIM today, you get:

- **Deployment-level TPM/RPM limits** — throttling that applies to *all callers combined*, not per user
- **Azure RBAC** — coarse-grained roles: Cognitive Services User gets access to everything, or nothing
- **A shared API key or Entra auth** — either one key that all developers share (no attribution), or RBAC that grants blanket access with no quota
- **Azure Monitor metrics** — aggregate token consumption across the deployment, not broken down by who consumed what

That works fine when you have three engineers sharing a dev environment. It breaks when you have 200 developers across 12 teams, each expecting a fair share of a limited TPM budget.

## The gaps FoundryGate fills

  <Card title="Per-developer token budgets" icon="bars">

  </Card>
  <Card title="Individual APIM subscription keys" icon="key">

  <Card title="Entra-synced provisioning" icon="setting">
    When a developer joins a FoundryGate-linked Entra group, they're automatically provisioned: user record created, key issued, quota resolved. When they leave, the key is revoked. No manual admin work.
  </Card>
  <Card title="Self-service for developers" icon="list-format">
    Developers sign in with their Entra account, see their current quota and usage, rotate their own key, and request a quota increase with a justification — all without contacting IT.
  </Card>

## The comparison

| Capability | Azure AI Foundry alone | With FoundryGate |
|---|---|---|
| Per-developer token budget | ❌ Deployment-level only | ✅ Per user, per month |
| Individual API keys | ❌ Shared key or RBAC | ✅ One APIM subscription per developer |
| Hard quota enforcement | ❌ No blocking mechanism | ✅ Real-time `403` at the gateway when the monthly budget is spent |
| Per-developer burst control | ❌ One developer can saturate the deployment | ✅ Per-developer TPM cap → targeted `429 + Retry-After` |
| Entra-based auto-provisioning | ❌ Manual RBAC assignment | ✅ Group sync → key + quota |
| Automatic deprovisioning | ❌ Manual RBAC removal | ✅ Departure detected → key deleted |
| Monthly reset | ❌ Manual | ✅ Azure Function fires at 00:01 UTC on the 1st |
| Quota increase workflow | ❌ None | ✅ Submit → admin approves → quota applied |
| Per-developer usage visibility | ❌ Aggregate only | ✅ Dashboard + audit log per user |
| Model deployment management | ❌ Portal only | ✅ Admin UI in FoundryGate |
| Deployment-level rate limits (TPM/RPM) | ⚠️ Shared ceiling, 429s passed to callers | ⚠️ Mitigated — backend pools + circuit breakers reroute around saturated deployments; the platform ceiling itself remains |

## How it works

FoundryGate sets up the gateway (Azure API Management) and the AI model deployments (Azure AI Foundry) for you, inside your own Azure subscription, and then *governs* access to them.

**Key provisioning**: When a developer first signs in, FoundryGate calls the APIM Management API to create an APIM subscription under the developer's budget tier (Standard, Power or Unlimited). The key is issued to the developer. Foundry never knows about individual developers — APIM does.

**Quota enforcement**: The gateway itself enforces each developer's budget in real time. APIM's `llm-token-limit` policy, keyed on the developer's subscription, carries their monthly token quota (requests return `403` the moment it's spent — no polling lag) and a per-minute token cap (bursts get `429 + Retry-After`, which coding CLIs back off on automatically). Budgets reset with the UTC calendar month on their own. A reconciliation Function keeps the dashboard's usage and cost figures authoritative from the gateway's request logs.

<Aside type="caution">
**Two separate layers.** FoundryGate's per-developer budgets and caps ride on top of Microsoft Foundry's own deployment-level rate pools (requests per minute, uncached-input tokens per minute, output tokens per minute for Claude), which are shared across all callers. FoundryGate *mitigates* saturation — per-developer caps keep any one person from exhausting the pool, and multi-deployment backend pools reroute around 429s — but it cannot manufacture capacity beyond the platform's ceilings. See [Azure AI Foundry Rate Limits](/foundry-gate/reference/azure-rate-limits/) for the current numbers and [Feasibility &amp; Strategic Direction](/foundry-gate/architecture/feasibility/) for how the mitigation works.
</Aside>

**Entra sync**: FoundryGate uses the Microsoft Graph API (app-only credentials) to read your Entra directory. Developers in a linked Entra group are auto-provisioned. Developers who leave the group are auto-deprovisioned. The sync runs on demand or can be triggered automatically.

<Aside type="tip">
FoundryGate is open-source and designed to be forked. Everything it creates — the gateway, the model deployments, its own database — lives in **your** Azure subscription, and sign-in uses **your** Entra tenant. No data leaves your Azure subscription.
</Aside>

## Who it's for

FoundryGate is for platform and infrastructure teams who want to:

- Roll out Azure AI Foundry access to the whole organisation without a quota free-for-all
- Give individual developers accountability over their AI usage
- Automate the access lifecycle instead of managing RBAC spreadsheets
- Let developers self-serve without opening up the Azure portal to everyone
